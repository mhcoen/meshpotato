# Reception explanations

[Back to the README](../README.md#features) | [Context and knowledge](context-and-knowledge.md)

Ask a normal question such as:

```text
How did my message reach you?
How strong was my signal at your radio?
Was my question received directly or over repeaters?
```

For a question about reception (signal, RSSI, SNR, hops, whether it heard
you) the model receives a small labelled block with the RSSI in dBm, SNR in dB,
and reported hop count attached to that delivered question, and the active
persona is told to state those numbers plainly first. Other messages do not
carry the block: given the numbers on every message, the model recited them
in reply to greetings and remarks. For example, given
RSSI -104, SNR -6.25 and five reported hops, an illustrative answer is:

```text
@[Ckemtp] Reported hops 5, RSSI -104 dBm and SNR -6.25 dB at my radio, possibly from different copies.
```

Wording is generated by the model, not a fixed template. `/serious` makes the
voice direct and factual; it switches silently, applies to the whole channel,
and expires after the same configured timeout as other personalities. `/reset`
restores the configured default immediately.

## What the measurements mean

- They describe reception at the bot, not signal conditions at every repeater.
- Hop count does not identify which repeaters forwarded the message. A zero
  means no repeater hops were reported, not proof of an authenticated route.
- Successfully receiving one question does not prove the link is reliable or
  that the answer will reach the sender.
- The measurements describe the question asking for the explanation, not the
  sender's previous message. The bot keeps no new per-person measurement cache.

The installed MeshCore library supplies uppercase `SNR` and, when available,
`RSSI` fields on the delivered channel event. V3 firmware supplies SNR directly;
RSSI is attached by the library from the latest matching decrypted RX-log copy,
which may have arrived via a different route. On older frames both RSSI and SNR
come from that heard copy, while hop count still comes from the delivered frame.
The event does not explicitly label the frame version. Consequently the bot
labels each source and warns that these are not a verified single reception;
matching path lengths would not prove the copies are the same either. These are
message-associated readings, not a trace of every rebroadcast.
Buffered messages, older firmware, disabled RX-log decryption, or missing log
matches can leave readings unavailable. Invalid numbers and unknown hop-count
sentinels are also marked unavailable rather than guessed.

The bot never borrows the most recent global radio statistics or an unrelated
heard packet to fill gaps. It snapshots the event values before queueing, so a
later message cannot replace them while the answer waits. No extra radio polls,
trace requests, or transmissions are made to obtain the information.

Reception context passes the same assembled-context injection checks as other
background and stays with the question through shortening retries. Replies use
the existing single-packet size checks, queue, and airtime controls. The model is
instructed not to invent missing measurements, but generated explanations can
still be wrong. Reception is discussed only when asked or relevant.
